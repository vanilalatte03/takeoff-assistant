# Takeoff Assistant — 실사용 검증 및 AI 산출 보조 PRD

- **문서 버전:** 0.1 요구사항 / 구현 현황 동기화 2026-11-06
- **기준:** 현재 `main` 브랜치의 로컬 웹 MVP 및 기존 `docs/PRD.md`
- **범위:** 기존 기능 개선 + 4차 데이터셋/검증 기반 + 5차 AI 보조 기능의 첫 수직 기능
- **상태:** 로컬 검색·이름 기반 도면 선택·AI 검색 조건 추출·검수 계산 초안·원본 대조·선택 영역 Vision·평가 기록 구현. 2026-11-05 기록 기준 요구사항 9/12의 개발자 검증을 확인했으며, 현업 정답·실제 도면 판독 품질·실사용 비교(R-04/11/12)는 부분 진행이다. 상세 근거는 [요구사항 감사](AI_ASSIST_AUDIT.md)와 [진행 기록](AI_ASSIST_PROGRESS.md)을 따른다.

## 1. 배경과 문제

건축 마감 수량산출 담당자는 PDF 도면 세트에서 마감표, 평면도, 상세도를 오가며 실 번호, 마감 코드, 치수, 벽체 타입, 공제 조건을 확인하고 계산식을 Excel로 옮긴다. 기존 인터뷰에 따르면 산출 항목 하나에 평균 약 3개 도면을 참조하며, 치수가 없을 때는 축척을 이용해 직접 측정한다. 작업은 반복적이지만, 공종·도면·시방서별 예외가 많아 무검수 자동 확정은 위험하다.

**문제 정의:** 사용자는 특정 산출 항목을 계산하기 위해 관련 도면과 치수를 반복 탐색한다. 탐색·대조·전사 시간이 크고, 도면 출처나 공제 근거를 놓치면 검수가 어려워진다.

**제품 가설:** 도면/마감 정보를 구조화하고 AI가 *근거가 있는 후보만* 찾아준다면, 계산 정확도를 해치지 않으면서 탐색 및 초안 작성 시간을 줄일 수 있다.

## 2. 제품 목표 및 비목표

### 목표
1. 기존 앱에서 업무 예제 2건을 사용자가 수동으로 끝까지 재현할 수 있다.
2. 사용자가 실 번호와 산출 항목을 요청하면 AI가 적절한 마감표·평면도·상세도 후보와 원본 근거를 제시한다.
3. 사용자 승인 전에는 AI 산출 결과가 **절대로 `CONFIRMED`** 상태가 되지 않는다.
4. 계산은 기존의 결정론적 `calculation_engine.py`가 수행하며, 식·수량·단위·출처·검수 상태를 기록한다.
5. 사람이 검수한 정답 데이터셋과 동일한 조건에서 규칙 기반 처리/AI 보조 처리를 비교 평가한다.
6. 아버지가 복귀했을 때 실제 도면 1세트로 사용성 및 작업시간을 검증할 수 있다.

### 이번 단계에서 하지 않을 일
- PDF를 업로드하면 모든 공종의 확정 견적서를 자동 생성하는 기능
- AI가 치수나 자재 코드를 추정한 뒤 근거 없이 확정하는 기능
- 재료 단가, 노무비, 간접비까지 포함한 공사비 견적 자동화
- 모든 스캔 도면/OCR, CAD/DWG 직접 처리, 자동 방 경계·공제 인식
- 다중 사용자 권한, 클라우드 공개 배포, XCost 등 외부 시스템 연동
- 여러 개의 전문 에이전트를 미리 분할하는 멀티 에이전트 플랫폼

## 3. 사용자와 핵심 시나리오

**1차 사용자:** 건축 마감 물량산출 업무를 수행하는 실무자 1명. **개발·검증 사용자:** 프로젝트 개발자.

### 시나리오 A — 110호 ACST 천장 면적
1. 사용자가 관련 PDF 도면 세트를 업로드하고 프로젝트를 선택한다.
2. 사용자가 `110호 ACST 천장 면적 찾아줘`라고 요청한다.
3. 시스템은 마감표(예: `AE601`)에서 Room 110과 ACST 정보를 찾고, 관련 평면/천장 도면(예: `AE101`, `AE103`)을 검색한다.
4. 시스템이 `4.2m × 2.7m`라는 치수 후보와 *어디에서 찾았는지*를 제시한다. 도면에서 치수가 확인되지 않으면 추측하지 않고 수동 스케일 측정을 요청한다.
5. 계산 엔진이 **공제 전 단순 예시 기준** `4.2 × 2.7 = 11.34㎡`를 계산한다.
6. 사용자가 공제 필요 여부를 확인하고 `NEEDS_REVIEW` 또는 `DRAFT` 초안을 검토한 뒤 명시적으로 확정한다.

### 시나리오 B — 119호 5A 파티션 면적
1. 사용자가 `119호 5A 파티션 산출해줘`라고 요청한다.
2. 시스템은 관련 파티션 키플랜과 상세도(예: `AE405` ~ `AE407`)의 후보를 제시한다.
3. 벽 길이 4.2m와 적용 높이 4.6m가 확인되는 경우 **공제 전·산출 면 수 1** 가정에 따라 `19.32㎡` 초안을 계산한다.
4. `5A` 의미, 해당 벽체의 산출 면 수, 개구부 공제, 적용 높이는 도면/시방서 또는 실무자의 판단으로 확인하도록 표시한다.

> 위 AE 번호는 **예제 도면에만 적용되는 식별자**다. 일반 도면에서 특정 도면 번호를 고정 규칙으로 사용하지 않는다.

## 4. 현재 제품 기반

- **기구현:** FastAPI + SQLAlchemy + SQLite, React/TypeScript, PyMuPDF, PDF 검색/분류, 마감표·치수 후보, 수동 측정, 계산, Excel(Summary/Details/Review), 검수 상태. 이름 기반 프로젝트/PDF 선택, 로컬/선택적 AI 검색, 사용자 검수 입력의 DRAFT 저장, 원본 대조, 선택 영역 Vision과 비교 기록도 제공한다. 구현 계약은 [API 안내](AI_ASSIST_API.md)와 [화면 안내](AI_ASSIST_UI.md)를 따른다.
- **제약:** 영어/텍스트 PDF 중심 휴리스틱; 스캔 OCR과 자동 방 경계/치수선 판독 부재; 실제 실무 정답 및 시간 절감 효과 미검증.
- **재사용 원칙:** 기존 서비스와 데이터 모델을 우선 재사용한다. 기존 `CONFIRMED` 보호, `REJECTED` 제외, 계산 입력/근거 저장 계약을 깨지 않는다.

## 6. 에이전트 동작 설계

현재 구현에서 모델은 요청 문장으로부터 `search_sheets` 인자를 한 번 반환한다. 서버가 선택된 PDF 범위 안에서 검색·마감 조회·근거 생성을 수행하며, 도면 원문을 모델에 재전송하거나 모델 자유 서술을 근거로 표시하지 않는다. 계산 초안은 사용자가 출처·단위·공제 등을 확인한 후 기존 계산 엔진으로 저장한다. 선택 영역 Vision은 별도 명시적 전송 확인이 필요한 기능이다.

아래 도구 목록과 실행 순서는 요구사항의 논리적 설계다. 모델이 여러 도구를 자율 반복 호출하는 다단계 에이전트가 구현됐다는 뜻은 아니다. 다단계 탐색은 검색 기준선과 추가 전송 정책을 마련한 뒤 별도 실험으로 판단한다.

설계상 도구(현재 API와 일대일로 같은 모델 공개 도구 목록이 아님):
- `search_sheets(project_id, room_query, role?, keyword?)`: 관련 페이지와 검색 근거 반환.
- `get_room_finishes(drawing_file_id, room_no)`: 확인 가능한 마감 후보 반환.
- `find_dimension_candidates(drawing_file_id, page_index, region?)`: 숫자·단위·원문·좌표 후보 반환.
- `calculate_quantity(calculation_type, inputs, deductions?, source_sheets)`: **기존 계산 엔진** 호출; 검증된 계산식과 수량 반환.
- `create_measurement_draft(...)`: 검증된 산출 초안을 미확정 상태로 저장. *사용자 승인 없는 확정 기능은 에이전트에 노출하지 않음*.

**실행 순서:** 사용자 요청 → 도면/마감 검색 → 필요 시 치수 후보 검색 → 누락·충돌 확인 → 계산 도구 → 근거 표시 → 사용자가 수정/승인 → 저장 및 Excel 반영.

**실패 처리:** 검색 결과 0건/다중 후보/단위 불명/상충 치수/이미지 품질 저하는 사용자 확인 요청 또는 수동 입력으로 전환한다. AI가 임의의 치수·도면 번호·확정 여부를 만들어내지 못하도록 서버에서 검증한다.

**근거 스키마(초안):** 프로젝트/파일 ID, 시트 번호, PDF 페이지 인덱스, 원문, 추출 방식(rule/text/vision/manual), bounding box(있는 경우), 정규화 값·단위, 가정·경고, 모델/도구 실행 식별자.

## 7. 도메인 규칙 관리

- 산출 유형별 `required_inputs`, `formula_type`, `unit`, `deduction_policy`, `side_multiplier_policy`, `evidence_required`, `review_questions`를 별도 정책 계층으로 관리한다.
- **인터뷰에서 나온 관행을 보편 법칙으로 하드코딩하지 않는다.** 예: GWB 양면 산출은 현장·재료·항목에 따라 확인이 필요한 규칙으로 저장한다.
- 모든 결과는 `원본 치수 → 단위 변환 → 공제 → 적용 면 수 → 최종 수량`을 역추적할 수 있어야 한다.
- 기본 수량 표시는 소수 둘째 자리까지이며, 정밀 계산/반올림 정책은 기존 계약 및 실제 현장 기준을 재검토한다.
- 건축 적산 일반 기준은 참고자료이고, 프로젝트별 도면·시방서·계약 기준이 우선한다.

## 8. 평가 계획

### 고정 평가 케이스
- E-01: 110호 ACST 천장, `4.2 × 2.7 = 11.34㎡` (공제 전 가정)
- E-02: 119호 5A 파티션, `4.2 × 4.6 = 19.32㎡` (단면·공제 전 가정)
- E-03: 필요한 치수가 없는 도면 → 추측하지 않고 수동 확인 요청
- E-04: 동일 실 번호가 여러 시트에 존재 → 시트 후보와 경고 표시
- E-05: 단위가 불명확한 후보 → 무단 정규화/확정 금지
- E-06: 사용자가 `CONFIRMED`한 행에 AI 재실행 → 명시적 재검토 없이 덮어쓰기 금지

### 지표
- **정확성:** 정답 항목별 수량/단위/마감 코드 일치율, 출처 시트 일치율, 공제 누락/과다 적용 건수.
- **에이전트 품질:** 관련 도면 검색 성공률, 잘못된 근거 인용률, 도구 호출 실패율, 수동 개입 횟수.
- **업무 효율:** 과제별 총 소요시간(재검토/수정 포함), 클릭·도면 이동 횟수, 사용자 수정 횟수.
- **안전성:** 무단 `CONFIRMED` 0건, 근거 없는 수량 확정 0건 (필수 게이트).
- **비용/운영:** 요청당 토큰/비용, 지연시간, 오류율.

초기 평가 데이터가 2개이므로 품질 백분율을 일반 성능처럼 홍보하지 않는다. 기준선 측정 후 목표치를 설정하고, 실제 사용자 검증 전까지 실무 정확도·시간 단축 성과를 주장하지 않는다.

## 9. 개인정보·보안·배포

- 현재 로컬 우선 제품 정책을 유지한다.
- 고객·발주처 도면은 외부 모델 API로 보내기 전에 소유자의 이용 허가와 기밀 여부를 확인한다.
- API 전송 전 선택 영역 최소화/개인정보·프로젝트 식별정보 제거를 검토한다.
- 키는 서버 환경변수/비밀 관리에 보관하고 UI, 로그, Git에 기록하지 않는다.
- 모델 출력은 신뢰되지 않는 입력으로 취급한다. 도구 호출 인자 검증, 프로젝트 범위 제한, 경로 조작 방지, 호출 횟수·비용 제한을 적용한다.
- API 사용이 불가하거나 금지된 환경에서도 기존 수동 측정·계산 기능이 유지되어야 한다.
- 클라우드 공개 배포 또는 외부 사용자 확장 전 인증·권한·백업·접근 통제를 별도로 설계한다.

## 10. 구현 단계 및 출시 게이트

### Phase A — 도메인/검증 기반 (AI 없음)
- 실제 예제 2건 E2E 수동 재현 및 테스트 작성.
- 현행 앱의 프로젝트/도면 선택 UX 개선.
- 도메인 규칙표와 공개 가능한 합성 데이터셋 작성.
- **게이트:** 수동 재현 계산식/수량/출처 정확, 기존 회귀 테스트 통과.

### Phase B — 첫 AI 수직 기능
- 단일 에이전트와 도면 검색·마감 조회 도구 연결.
- `110호 ACST 천장 면적` 요청에서 관련 페이지와 출처를 표시.
- **게이트:** 근거 없는 답변 시 실패/확인 요청, 기존 데이터 무단 수정 없음.

### Phase C — 계산 초안 생성
- 치수 후보 및 계산 도구 연결, 미확정 초안 생성.
- 수정·검수 UI, 실행 로그, 테스트 케이스 E-01~E-06 통과.
- **게이트:** 무단 확정 0건, 기존 수동 흐름 및 Excel 유지.

### Phase D — Vision/OCR과 실사용 검증
- 실제 실패 유형에만 이미지 해석 후보 추가.
- 아버지가 사용 권한을 가진 실제 도면으로 업무 테스트.
- 기준선 대비 시간·정확성·수정 부담 분석 후 개선 순위 결정.
- **게이트:** 실무자가 최종 결과를 검수하고 채택 가능 여부를 판단.

## 11. 결정 필요 사항 / 미확인 사실

1. 실제 최종 Excel이 요약 합계만 필요한지, 상세 계산 근거를 어느 수준까지 요구하는지.
2. 건축 적산 범위가 실내 마감 중심인지, 설비/기타 공종까지 포함해야 하는지.
3. 파티션 타입별 실무 산출 면 수와 공제 기준을 어떤 문서에서 확인하는지.
4. 스캔 PDF의 빈도 및 외부 AI API로 도면 전송이 가능한지.
5. 실무 사용 환경(Windows 설치형/브라우저, 인터넷 연결, 파일 크기, PDF 페이지 수).
6. 실제 도면과 최종 산출표를 비교할 수 있는 승인된 정답 샘플의 확보 가능 여부.

위 항목은 미확정으로 명시하고 임의의 제품 정책으로 단정하지 않는다.

## 12. 후속 개발과 실무 검증

기존의 합성 기준 사례·규칙표·프로젝트/PDF 선택·탐색·계산 초안·실행 로그는 PR #11~#15에 반영됐다. 같은 기능을 새로 구현하는 대신 [사용성·평가 phase](../phases/6-usability-evaluation/README.md)를 따른다.

1. 구현 현황과 안내를 동기화한다.
2. 검수된 평가 사례만 불러오는 기반을 만들고, 검색 품질 기준선을 별도 PR로 측정한다.
3. 한 과제의 업로드부터 검수·Excel까지 이어지는 흐름과 Windows 실행·종료를 단순화한다.
4. Vision 실패 조건을 합성 자료로 확대 평가한다.
5. 기존 수작업 / 로컬 보조 / AI 보조를 구분한 파일럿을 준비하고, 실무자의 초기 관찰 결과를 다음 수정에 반영한다.

실무 정답 20~50건의 승인, 실제 도면 전송 권한, 아버님의 사용·검수·시간 비교는 외부 게이트다. 평가 도구나 화면 구현만으로 R-04/11/12를 완료하지 않는다. 다단계 AI 확장은 기존 검색보다 효과가 있다는 근거를 얻을 때 선택적으로 진행한다.
